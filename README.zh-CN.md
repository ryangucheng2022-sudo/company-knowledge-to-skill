# Company Knowledge to Skill（公司知识转技能）

[English](README.md) | 简体中文

一个通用、可复用的 Skill：从多个 AI 或人工输入中采集某个组织专属的知识，对齐差异、实施隐私控制，生成下游 Skill，并对结果进行测试验证。

## 这个项目解决什么问题

企业大量有价值的知识存在于员工经验、日常工作和历史决策中，却没有变成 AI 可以持续使用的组织能力。本 Skill 探索的正是一条转化路径：将分散在不同人、不同 AI 和不同工作资料中的隐性知识，转化为**可复用、可验证、可持续迭代**的 AI 能力。它不只是“让 AI 写得更像企业员工”。

它针对的是企业知识管理的三个核心问题：

- **知识分散**——在人脑、AI 记忆、文件和系统中；
- **知识失真**——口径不一、版本冲突、理解错误；
- **知识难执行**——只有文档，没有标准任务方法。

传统知识库解决“在哪里找到知识”，Skill 进一步解决“如何按照这些知识完成工作”：知识库可以告诉 AI 某个术语是什么意思，业务 Skill 则能规定如何筛选数据、怎样分析变化、什么情况属于异常、以及如何验证结果。当然，Skill 并不会因为封装了知识就自动可靠，仍需要数据权限、工具连接、测试和人工监督。

## 与知识库、RAG、Agent 的区别

| 能力 | 主要解决什么问题 |
|---|---|
| 知识库 | 保存、分类和查找知识 |
| RAG | 在 AI 回答问题时检索相关知识 |
| Agent | 根据目标调用工具并执行任务 |
| **Knowledge-to-Skill（本项目）** | 将分散知识提炼为规范、流程、判断规则和可测试的 Skill |

它不替代三者，而是补齐其中缺失的知识工程化环节：企业已经有很多文档，缺的是从文档、经验和反馈中提炼可执行方法的标准化流程。

## 六个典型应用场景

1. **企业 AI 应用标准化**——员工已在用不同的 AI，输出的术语、业务理解和表达风格不一致；统一采集与规范化形成企业级 AI 知识与表达标准，减少重复解释、术语错误和文稿返工。
2. **专家经验沉淀与传承**——专家如何分析问题、判断异常、处理例外，往往只在个人经验中；多轮采集与案例验证可将其转化为标准工作方法，降低关键人员依赖。
3. **新员工入职与岗位交接**——新人需要的不仅是制度写了什么，还有内部术语、真实工作流程、历史判断和部门责任边界；缩短熟悉业务的时间，降低交接中的知识损失。
4. **专业业务 Agent 开发**——财务分析、销售项目分析、供应链预警等任务需要企业自己的指标定义、业务规则、判断标准与分析方法，而不只是通用推理。
5. **并购整合与跨组织协同**——不同公司、事业部可能同词不同义、或以不同流程完成相同任务；识别定义冲突和管理差异，统一必要口径，同时保留合理的业务差异。
6. **多 AI 平台迁移与知识复用**——积累在一个平台里的工作上下文容易被锁定；形成独立于 AI 模型的企业知识资产，降低迁移、替换和重复训练成本。

## 商业价值的四个层级

| 价值层级 | 主要价值 | 可衡量指标 |
|---|---|---|
| L1 效率提升 | 减少术语解释、文稿修订、资料查找 | 单项任务耗时、返工次数 |
| L2 质量提升 | 降低业务口径和事实错误 | 术语准确率、重大错误率 |
| L3 知识复用 | 让专家方法被更多员工和 Agent 使用 | Skill 复用次数、覆盖岗位数 |
| L4 组织能力 | 减少关键人员依赖，增强跨团队协作 | 新人上手周期、交接成功率、流程执行一致性 |

L1、L2 最容易在短期内验证；L3、L4 潜在价值更大，但需要更长时间和真实业务应用才能证明。建议的优先验证顺序是：企业术语与 AI 表达规范 → 专业岗位知识与分析方法 → 岗位交接与组织知识传承。

从产品形态看还可以分两型：工具型（面向个人或团队，把自己的 AI 对话与工作经验转成 Skill，容易推广）与企业型（面向组织，增加知识来源管理、权限控制、版本治理、人工审核、效果评估和持续更新，长期价值更高）。企业型必须守住一条前提：采集员工 AI 历史对话须以明确授权和数据最小化为前提，个人聊天记录不能默认视为企业可收集的资产。

长期看，这个方向可以理解为三个阶段：知识提取（让隐性知识可见）→ Skill 工程（让知识可以执行）→ 组织学习（AI 在执行中识别规则不足、提出更新建议、经审核后更新并回归测试）。前两个阶段是本项目已能直接验证的；第三阶段的机制——持续纠正闭环——已在 `references/correction-loop.md` 中给出。

> 让企业知识不再只沉淀在文档里、留在员工脑海中，而是转化为组织和 AI 都能够持续复用的工作能力。


## 方法总览

| 阶段 | 输入 | 产出 | 人工检查点 |
|---|---|---|---|
| 采集 Collect | 范围＋来源清单 | 多个独立采集者的输出 | 范围与敏感边界经确认 |
| 归一化 Normalize | 采集输出 | 带来源出处的标准记录 | 抽查记录与原文是否一致 |
| 对账 Reconcile | 全部记录 | 去重后的记录＋冲突日志 | 批量决策单一次性拍板 |
| 提炼 Specify | 对账后的记录 | 术语、规则、表达与纠偏指南 | 复核定级（执行防虚高封顶） |
| 生成 Generate | 已验证记录 | 知识包／下游 Skill（自带已知缺口一节） | 卫生闸门：100% 已定级、无占位条目 |
| 评测 Evaluate | 技能包＋用例 | 行为结果（充分／部分／缺失，及否决项） | 缺口接受还是打回 |
| 维护 Maintain | 使用中发现的错误 | 登记表更新＋新增回归用例 | 纠正攒批处理，不逐条打断 |

## 设计原理

- **先独立采集，后求共识**：采集者按同一契约独立工作、互不可见。一致是证据，分歧是信号——若从一份草稿出发采集，两者都会丢掉。
- **先定基线，再谈合并**：指定一个来源为基线，任何版本不得静默覆盖它；被替代的版本降级留痕、永不删除。
- **定级靠挣，不靠自称**：来源的自评只是主张。讨论阶段的内容先封顶，有正式证据才升级，且每条定级都要记录依据。
- **技能包是构建产物**：登记表是唯一事实源，生成的包只能由它重新生成、禁止手改副本；且包必须诚实列出自己不覆盖什么。

## 快速开始

1. 复制 `templates/source-inventory.yaml`，定义范围、受众、来源与敏感等级。
2. 按 `references/collection-prompts.md` 中的统一契约，运行多个独立采集者。
3. 按 `references/knowledge-schema.yaml` 的结构将输出归一化。
4. 去重并记录冲突。批准状态、时间口径、权威性或受限数据必须经人工检查点确认。
5. 生成目标知识包或下游 Skill，公司事实与通用方法指令分开存放。
6. 用 `scripts/validate_knowledge.py` 校验 JSON/JSONL 记录，并执行 `references/evaluation-cases.yaml` 中的全部用例。

本包只包含占位内容。用于具体组织时，请替换为有授权、有来源依据的真实内容。

## 完整示例

`examples/meridian-office-furniture/` 以一家虚构公司完整跑通了全流程：两份采集者输出、归一化记录（`records.jsonl` / `records.yaml`）和一份冲突日志。示例刻意包含了一处多 AI 冲突、一处隐私泄漏、一处夸大表述、一对同义词、一条随时间变化的规则和一个缺失的负责人——与七个评测用例一一对应。

## 验证结果（2026-11-05 实跑）

对示例的校验（9 条记录）：

```text
$ python3 scripts/validate_knowledge.py examples/meridian-office-furniture/records.jsonl --export generic
records=9  errors=0  warnings=1   （第 5 条：confidential — 通用导出前需抽象/打码/剔除）
$ python3 scripts/validate_knowledge.py examples/meridian-office-furniture/records.jsonl --export internal
records=9  errors=0  warnings=0
$ python3 scripts/validate_knowledge.py examples/meridian-office-furniture/records.yaml --export generic
records=9  errors=0  warnings=1   （与 JSONL 结果一致 — 已支持 YAML 输入，需要 PyYAML）
```

负向测试（构造了缺失 `provenance`、重复 `record_id`、`proposed` 记录谎称 `high` 可信度的文件）正确失败：`errors=3, warnings=1`，退出码 1。

`references/evaluation-cases.yaml` 中的七个用例全部被该示例演练，对应关系记录在示例的 README 中。

**一致性（漂移）检查**：登记表是正本、技能包是构建产物；`python3 scripts/check_consistency.py` 校验包没有与自身脱节：已发布文件在 SKILL.md 中都有出处、引用的参考与模板都存在、演练示例在两种导出模式下仍通过校验器。当前结果：0 错误、0 警告。

## v1.1.0 更新

以一次真实企业部署的经验加固（匿名化记录见 `references/field-failure-patterns.md`）：

- 基线指定与静默覆盖禁令；被替代版本降级留痕、永不删除
- 定级防虚高：来源自评只是主张；新增 `status_basis` 字段逐条记录定级依据；讨论类内容封顶
- 批量决策单＋回写协议；常设待确认台账（open → decided → closed）
- 敏感标记须穿透摘录与转换；导出前数值扫描作为放行闸门
- 生成前登记表卫生闸门（100% 已定级、无元条目、无占位条目），校验脚本同步新增：重复条目报告、空条目/元条目检测、统一值启发式、`--scan-values` 扫描
- 纠偏案例对（一错一正）作为正式条目类型；生成的技能包须自带「已知缺口」一节；评测采用独立执行者协议

校验脚本对示例现同时报告 `rated_coverage=9/9`（其余默认输出不变：generic 为 errors=0、warnings=1；internal 为 errors=0、warnings=0）。构造的脏数据测试（占位条目、重复条目、元条目、全表同一状态、可导出条目中含未标记数值）正确失败：errors=1、warnings=7，退出码 1。
